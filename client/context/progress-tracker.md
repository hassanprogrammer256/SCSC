## Known Gaps / Deliberate Trims

Everything below was a conscious scope decision during the build, not an oversight — listed here so a future session doesn't have to rediscover them:

- **DS "Resources" nav item is the one remaining `ComingSoon` page in the whole system.** Academic-resource sharing is mentioned in `project-overview.md`'s broader feature list but is **not** one of `build-plan.md`'s 32 numbered features — it has no model, no scope decisions, nothing to build against. Flagged explicitly rather than silently built or silently left unexplained; needs an `/architect` pass (new model, upload/storage shape, who can see what) before it's picked up.
- **EgoSms/Gmail credentials are present but likely non-functional as of 2026-08-25** (see Production Readiness below for the full audit) — `EMAIL_HOST_PASSWORD` doesn't match Gmail's App Password format and `EGOSMS_SENDER_ID` exceeds the typical gateway sender-ID length limit. The integration code itself is correct and verified to fail gracefully regardless (Notification rows record `failed`, in-app notification still lands).
- **Google Programmable Search key looks malformed and `GOOGLE_SEARCH_CSE_ID` is still blank** (see Production Readiness below) — external plagiarism-source checking will not run either way (`PlagiarismReport.external_checked=False`), internal (cohort) comparison is unaffected. Even once genuinely configured, the free tier is **100 queries/day project-wide** (~10 checks/day at `EXTERNAL_SENTENCES_PER_CHECK=10`) — raise `PLAGIARISM_EXTERNAL_DAILY_QUOTA` once on a paid key, no code change needed.
- **Notice Board / Activity Feed (AdminDashboard) stay on mock data.** No real backend source exists for either — Notices would need Announcements reshaped as a feed (not built), and there's no audit-log feature anywhere in the 32-feature build plan to back a real Activity Feed.
- **MiniCalendar (DsDashboard) stays a decorative preview.** Phase 4's real `TimetablePage` is the actual timetable; the dashboard widget was never meant to be interactive.
- **Timetable calendar is month + list only** (no week/day sub-toggle) — a documented Phase 4 scope trim given a college course's actual lesson volume.
- **Marks are not deadline-gated** — `architecture.md`'s invariant mentions "deadline plus any Admin-configured grace period," but no grace-period field exists anywhere in the schema or build plan. Submissions *are* hard-gated by the deadline (the unambiguous part of that invariant).
- **Announcement "individual" scope pickers are checkboxes over the full officer/DS list** — fine at this college's roster size; would want a search/filter if the roster grows much larger.
- **Windows dev-server gotcha**, not a code issue: stale `manage.py runserver` processes can pile up on port 8000 across a long session (see the `windows-django-zombie-servers` memory entry) and silently serve pre-edit code. If a change "isn't taking effect," check `netstat -ano | grep :8000` for more than one LISTENING PID before re-debugging application code. This session ran the backend with `--noreload` for the second half specifically to sidestep it — a real dev session should just watch for the duplicate-PID symptom.

## Production Readiness

**Verdict as of 2026-08-25: not production-ready — infrastructure/config only, not application code.** All 32 build-plan features are implemented and were verified end-to-end throughout this project's build (server-side validation, role/permission scoping consistently enforced). The gap is entirely in deployment configuration. Full audit below; see `architecture.md` → Environment Configuration for the settings-side changes already made in response.

**Blockers (backend cannot serve any traffic like this):**
- `.env.production`'s `ALLOWED_HOSTS` and `DATABASE_URL` are both still blank — Django rejects every request (`DisallowedHost`) and there is no real database configured. Both need real values only the deployer has (hosting hostname, managed Postgres connection string).
- No deployment process exists anywhere (no Procfile, no platform config, nothing documented) — settings assume Postgres/Redis/Cloudinary/a WSGI server are provisioned somewhere, but nothing actually provisions or starts them.
- **Fixed this session**: `CORS_ALLOWED_ORIGINS` was JSON-array syntax (`["seniorcommand.netlify.app"]`) but the hand-rolled parser in `production.py` does a plain comma-split — corrected to a bare comma-separated origin list with scheme. `REDIS_URL` was a full `redis-cli -u ...` shell snippet copied from a provider dashboard, not a bare URL — corrected to just the `redis://...` part. No WSGI server was installed at all (`gunicorn` added to `requirements/production.txt`) and no static-file solution existed for Django's own `/admin/` assets (WhiteNoise added — middleware, `STATIC_ROOT`, `STATICFILES_STORAGE` in `production.py`). `client/.env.production` didn't exist at all (a production Vite build would have `VITE_API_BASE_URL` undefined) — created as a placeholder needing a real value.

**Configured but likely won't work once the blockers above are fixed** (all fail gracefully by design — won't crash anything, just won't do what they're for):
- `EMAIL_HOST_PASSWORD` doesn't match Gmail's 16-character App Password format — Gmail rejects a plain account password for SMTP once 2FA is on (required to generate an App Password in the first place). Needs a real App Password.
- `EGOSMS_SENDER_ID` is far past the ~11-character alphanumeric limit most SMS gateways (EgoSms included) enforce — likely rejected by their API. Needs shortening (e.g. "SCSC-JINJA").
- `GOOGLE_SEARCH_API_KEY` (in `.env.development`) doesn't match Google's key format (`AIza` + 35 chars) — looks like the wrong credential entirely. `GOOGLE_SEARCH_CSE_ID` is still blank; both required together.
- Cloudinary credentials are correctly *formatted* — not independently verified as valid/live.

**Security hygiene, independent of whether things work:** real-looking secrets (Gmail, EgoSms, Redis, Cloudinary) are sitting in plaintext in both `.env.development` and `.env.production`. Not in git history (this project isn't a git repo), but they've been pasted into chat during this session — treat all of them as potentially exposed and rotate before relying on them for anything real (Redis password + Cloudinary secret via their dashboards, a fresh Gmail App Password). Separately, worth reconsidering putting real, personal-looking credentials in the *dev* config at all — dev files tend to get handled far more casually than production secrets. In-place `NOTE:` comments were added directly in both `.env` files flagging each specific issue, so a future session (or a human deploying this) sees them at the point of use, not just here.

## Decisions Made During Build

- **2026-08-26** — Large-scale test data seeding, in response to explicit user request: "before i stage my app for production, first flush everything in the database and insert data for testing like atleast 100 students divided equally in the land groups, atleast 20 DSs, atleast 30 activities, scheduled and timetabled, create data that can be used to test atleast every feature of the system, saving media in local database." Built `common/management/commands/seed_test_data.py` — the existing `seed_demo_users` command only ever created 3 bare `User` rows for the login page's demo hints (no course/profile/land-group data at all), so this is a new, separate, much larger command rather than an extension of it. Key decisions: (1) Every seeded account (Admin/DS/Officer, both the main and archived course) shares one fixed test password rather than the real registration flow's random one-time password — deliberately different from real registration behavior, since the entire point of this dataset is to be able to log in as anyone and test. (2) Wherever real business logic already existed as a reusable function (`send_announcement` for recipient resolution + Notification fan-out, `run_plagiarism_check` for the plagiarism engine), the command calls that function directly rather than reimplementing the logic — safer and won't silently drift from the real behavior. Direct ORM creation was used only where the real serializer's validation didn't apply to fresh seed data anyway (registration's returning-army-number checks) or where correctness is trivially guaranteed by construction (weights summing to exactly 100.00, DS never double-booked across land groups for one activity, timetable rooms/times never overlapping — each satisfied by the generation algorithm itself, not by re-validating after the fact). (3) Officer/DS phone numbers and emails are deliberately left blank in seed data — `send_announcement` attempts a real SMS/email per recipient, and with 100+ recipients per course-wide announcement, populating fake contact info would mean hundreds of real network calls to EgoSms/Gmail during seeding for no benefit (in-app Notification rows, the actual thing being tested, are created regardless; `not_applicable` delivery status is itself a legitimate, testable state). (4) A second, smaller, already-archived course (2024/25) is seeded alongside the main active one specifically so the Archive feature (Phase 8) has something real to display — the user's specified quantities (100/20/30) were clearly about the one main course, but Archive can't be tested at all without a second course in that state. (5) One near-duplicate submission is deliberately seeded (4 officers submit the same paragraph, on the first past-deadline activity) and pre-checked via `run_plagiarism_check` — guarantees a real, discoverable plagiarism match exists rather than leaving that entirely to chance across randomly-assigned paragraph templates. Verified thoroughly: direct DB queries confirmed exact counts (100/50/50 officers, 20 DS, 30 activities summing to exactly 100.00, zero DS double-booking conflicts, 761 submission files + 22 avatar files actually written to local `media/`, matching the DB row counts exactly) before ever touching the browser. This scale of data — the first time the app had ever been exercised past `common/pagination.py`'s `PAGE_SIZE=20` in a real course — immediately surfaced two real, previously-invisible bugs, both now fixed: (a) **every single list-fetching Redux thunk in the app (12 slices: activities, assignments, officers, directing staff, submissions, marks, assessments, timetable, users, courses, notifications, announcements) only ever read page 1 of DRF's paginated response**, silently dropping every row past the 20th — e.g. Activities' weight-total badge summed only 20 of 30 activities and showed "66.7% remaining" for a course that was actually fully weighted. Fixed with one shared `fetchAllPages()` helper (`lib/apiClient.ts`) that crawls DRF's `next` cursor until exhausted, now used by all 12 thunks — this was invisible at every previous testing scale (Phase 2-8 verification never exceeded ~10-20 rows of anything) and would have silently broken in real production use with a real course roster. (b) **`WeightTotalBadge` and `ActivityFormModal`'s live weight preview displayed raw, unrounded floating-point sums** — realistic decimal weights (e.g. 3.33% × 30 activities) accumulate IEEE-754 rounding error under plain JS addition, landing at values like `99.99999999999996` that never satisfy `=== 100` and render as visual noise; small round numbers used in all earlier testing happened to sum cleanly by luck. Fixed by rounding for both the display text (`.toFixed(2)`) and the equality/threshold checks (`Math.round(total * 100) / 100`) in both components. Also discovered and cleaned up mid-session: 28 orphaned headless Chromium processes had accumulated across this project's extensive Playwright verification history and were causing new browser launches to hang — killed via `taskkill`, distinct from the already-documented Windows Django zombie-server gotcha but the same underlying pattern (long-running dev sessions accumulate orphaned child processes that need periodic cleanup).

- **2026-08-25** — Two follow-up fixes, in response to explicit user feedback: "you have not given the DS the privilege to download the submitted work. also the officer and directing staff creation forms don't have image upload for the user." Neither needed a full `/architect` session — both are additive, reuse already-established patterns, and have no ambiguous trigger model or new external dependency the way the plagiarism redesign did. (1) **Submission download**: added `file_url` as a new read-only `SerializerMethodField` on `_BaseSubmissionSerializer` (`default_storage.url()` + `request.build_absolute_uri()`, same resolution pattern as `User.avatar_url`) — deliberately placed on the *base* serializer, not DS-only, since a submission's file itself isn't sensitive data the way plagiarism analysis is; only the UI control was actually built on `MarkingRow` (DS), per the specific ask. (2) **Avatar upload at registration**: `personnel/serializers.py`'s `_BaseRegistrationSerializer` gained an optional write-only `avatar` `ImageField`, applied to the created/reused `User` in `_resolve_user`; `PersonnelIdentityFields` (shared by both Officer/DS register modals) gained the upload control (same visual pattern as `ProfilePage`'s photo picker, but with a live blob-URL preview instead of an immediate upload, since registration creates the user the photo belongs to); both registration Redux thunks switched from a JSON body to `multipart/form-data`. Caught and fixed a related pre-existing gap in the same pass: `OfficersPage`/`DirectingStaffPage`'s grid-view `Avatar` never received `src={user.avatarUrl}` at all — so even a successfully uploaded photo (via registration or via `ProfilePage`'s pre-existing self-service upload) was invisible everywhere in the admin roster, always falling back to initials. Verified end-to-end via Playwright + direct authenticated API calls: download link resolves to a real 200 response with the correct docx content-type; avatar upload at registration returns 201 with a populated `avatar_url`, confirmed for both Officer and Directing Staff; the new officer's roster card renders the actual uploaded photo, and Aisha's pre-existing self-service-uploaded photo now renders correctly too (previously always showed initials due to the `Avatar` `src` gap above). One test-only wrinkle worth noting for future sessions: mid-verification, one seeded officer's `land_group` was found to have silently changed from `red` to `blue` between two points in this same session, for reasons that couldn't be traced to any code path touched in this session (no code here writes `OfficerProfile.land_group` outside of initial registration) — treated as disposable dev/QA seed-data drift and corrected directly in the DB rather than investigated further, since it didn't correspond to any application code change.

- **2026-08-25** — Plagiarism checking redesigned end-to-end, in response to explicit user correction: "the plagiarism checking isn't automatic on work submission, rather, the DS runs it if he wants... a summary of output is returned, i.e the percentage of plagiarism, then highlighting the plagiarised or paraphrased content with different colors providing the possible source" — and, when asked, confirmed sources can be external web pages too, not just other officers' submissions. Went through a full `/architect` session first since this touches trigger model, data shape, a new external integration, and a genuinely hard technical question (TF-IDF/cosine is document-level; sentence-level "plagiarised vs paraphrased" highlighting needed a different approach). Key decisions: (1) **DS-triggered only** — `PlagiarismReport` is no longer created at `Submission.create()` time; a DS clicks "Run Plagiarism Check" per submission (`SubmissionViewSet.check_plagiarism`, `IsDirectingStaff`-only), always safe to re-run (fully overwrites). (2) **Admin loses all plagiarism visibility**, not just the trigger — was previously an oversight in the old code (`DsSubmissionSerializer` was handed to any non-Officer role, including Admin); now a dedicated `AdminSubmissionSerializer` (identical to Officer's, zero plagiarism fields) closes that gap. Confirmed the frontend never actually exposed this to Admin either (no Admin marking page exists), so this was purely a backend/API correction. (3) **Sentence-level granularity** — `split_sentences()` (plain regex splitter, no NLP dependency; documented limitation: doesn't special-case abbreviations like "Lt. Col.", only affects highlight granularity not comparison correctness) replaces whole-document comparison. Each sentence independently gets a band: `plagiarised` ≥75%, `paraphrased` 40–75%, `original` below (never flagged under `MIN_SENTENCE_WORDS`, to avoid noise on short generic sentences). (4) **Two source pools, both always attempted**: internal (every other Submission on the same AssessmentSchedule, TF-IDF/cosine, same tool as before just sentence-to-sentence) and external (Google Programmable Search, chosen over a dedicated paid plagiarism API to match this project's existing pattern of building against one general-purpose provider — see EgoSms/Gmail). External checking compares against the **search snippet only**, never fetches the actual external page (fetching arbitrary pages ourselves would add a lot of failure surface: paywalls, bot-blocking, JS-rendered content) — accepted as a real accuracy trade-off, discussed explicitly rather than silently built. (5) **External query volume capped at the 10 most distinctive sentences per check** (longest/least-generic), run through a small thread pool since they're independent I/O-bound calls — sized against Google's free-tier cap of 100 queries/day *project-wide*, not per check. (6) **Daily quota tracked via a new `ExternalSearchQuota` model** (date + count); a check that would exceed the cap silently skips external comparison for that run (not an error) — internal comparison always still runs, and `PlagiarismReport.external_checked` records whether the web step actually happened. (7) **`Submission.extracted_text` caches parsed docx/pdf text** after first extraction — the old automatic version re-parsed every other submission's file from disk on every single run with no caching, which was fine when it ran exactly once per submission but not once re-running became an expected DS action. `warm_cohort_cache` eagerly extracts the whole assessment's cohort on whichever check happens to run first for that assessment — a one-time cost per assessment (measured: ~0.2–0.5s once warm vs. up to several seconds cold for a pdf-heavy cohort), not per check. (8) Verified end-to-end in a real browser via Playwright against real submission data (a synthetic duplicate submission created for the test, cleaned up afterward): a submission starts "Not Checked" → DS clicks "Run Plagiarism Check" → chip updates to "100% — High similarity" (correctly matching its duplicate peer) → "View Report" opens a modal showing the overall score, a "web sources: not checked (daily limit reached, or not configured)" note (correctly reflecting blank `.env` credentials), a Plagiarised/Paraphrased legend, and the actual submission text with the matching sentence highlighted — confirmed only the clicked row's submission was affected, not its cohort peers. Confirmed via direct authenticated API calls (bypassing the frontend entirely, for a server-authoritative check): Admin's submissions response has zero `plagiarism_*` keys; Officer's is likewise unaffected; an Officer attempting `check-plagiarism` gets a 403. Zero console errors, zero failed requests throughout the DS flow.
